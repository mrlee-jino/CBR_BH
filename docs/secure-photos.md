# Secure property photos

Owners can upload actual property photos, choose a cover, remove a photo, and read admin feedback. Admins review each photo before publishing the property. New uploads and photo changes to a published listing pause publication and require another property review. A pending upload never appears publicly.

## Hosted activation

1. Apply migrations 001–004 first. Existing installations then run `supabase/upgrade-photos.sql` once in Supabase SQL Editor. Do not rerun bootstrap or older upgrades. New installations use `bootstrap.sql`, which includes all five migrations.
2. In Supabase project settings, obtain a server secret key (`sb_secret_...`) or the legacy `service_role` key. Enter it securely as `SUPABASE_SECRET_KEY` in Vercel's server environment for this project, then redeploy. Also set `NEXT_PUBLIC_SITE_URL` to the exact canonical website origin; upload requests must come from that origin. The legacy variable `SUPABASE_SERVICE_ROLE_KEY` is also supported. Use a key from the same project as `NEXT_PUBLIC_SUPABASE_URL`. Never prefix this variable with `NEXT_PUBLIC_`, commit its value, or paste it into chat. This key is privileged and is never sent to browsers. The local test helper supplies a separate local-only key automatically.
3. Sign in as the verified owner. Upload a JPEG, PNG, or WebP under 3 MiB and 16 megapixels, write a useful description, then submit the property.
4. Sign in as an admin and verify MFA. Approve or reject each pending photo, then review the property. Publication is blocked while any ready photo still awaits review. Rejected photos stay private and can be removed by the owner after review.
5. Verify signed-out discovery and photo delivery on your deployment. This repository's tests use isolated local Supabase and do not establish hosted readiness.

## Processing and access

The upload route accepts at most 3 MiB of image bytes plus bounded form overhead, even without a trusted Content-Length. It rejects cross-origin requests, verifies the user with Auth, and reserves a photo through that user's JWT. SQL verifies ownership, email confirmation, account status, role, listing status, and quotas before image decoding. Limits are 12 current photos per property and 20 upload attempts per owner per hour; reservations are serialized across the owner's properties.

Sharp checks actual raster signatures and formats, rejects animation and oversized dimensions, autorotates, bounds output to 1600×1600, re-encodes to WebP, and drops embedded metadata including EXIF/GPS. Filenames and storage paths are generated by the server/database, never taken from the uploaded filename. Only the server can upload processed bytes and finalize a ready photo; the authenticated owner cannot mark an arbitrary object processed or approve it.

The private `property-photos` bucket continues to deny **all** direct anonymous/authenticated Storage access, including uploads, reads, and signing. The server key is used only after an explicit photo authorization RPC. `/media/photos/[id]` streams an authorized ready image: owners can see their private photos; MFA-verified admins can review them; everyone else sees only approved photos belonging to a published property with an active owner. Returned storage paths contain property/photo UUIDs, not owner identifiers.

Images are served with `private, no-store`, `Vary: Cookie`, and `nosniff`. The Next.js image optimizer is disabled so it cannot cache a withdrawn or private photo through `/_next/image`. No long-lived signed URLs or public bucket URLs are issued. Pausing a listing or removing a photo stops subsequent public image requests; already downloaded copies cannot be recalled.

## Cleanup and failures

Reservations expire for quota purposes after an hour. Invalid uploads are marked removed. If a completion response is uncertain, the route does not delete an object that might already be ready. Removed records retain their paths until the underlying files can be deleted. Admins can run **Clean up unused photos** in the admin workspace to remove expired reservations and removed files in batches. Run it regularly; retry after transient Storage errors. This is an explicit admin operation, not an automatically scheduled job.

Legacy photo rows created before this pipeline are treated as unprocessed and are never automatically exposed. Owners should upload them through the validated pipeline. Do not make the bucket public as a shortcut.

## First real property

Real listing imports must target an existing verified, active owner account. Keep exact addresses and contact phones in `property_private_details`, not descriptions, fixtures, logs, or committed seed files. Create drafts and rooms first, verify the information, add actual photos, then use the MFA-protected admin review flow. Do not mark an unreviewed listing verified or publish fictional test data.

## Validation

Image tests cover metadata stripping, autorotation, output sizing, raster/MIME validation, animation, and pixel/file limits. Database tests cover owner/server/admin boundaries, moderation gates, quotas, covers, removal, and public access revocation. Desktop/mobile browser tests exercise invalid and valid uploads, private delivery, photo review before publication, signed-out discovery, optimizer denial, removal, form validation, and accessibility. Every fixture/account/object belongs to the local test stack.
